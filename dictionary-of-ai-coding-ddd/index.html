1. 领域实体提炼

Matt 的 Curriculum.md 已经做了 7 个 Section 的切分，这与 DDD 的 Bounded Context 高度同构。每个 Section 的核心词条，就是该 Context 的 Aggregate Root 候选。我把 Section 标题直接用作 Context 名（沿用 Matt 的命名），不擅自重命名——domain.md 里明确说"用 glossary 定义的词，不要自己造同义词"。

聚合根 AR 实体 值对象 VO 领域事件 领域服务 仓储 Bounded Context

1.1 Section 1 — The Model（基础设施层）

这是字典里最底层的 Context——所有上层概念（Agent、Session、Tool）都要"踩"在它上面。它不依赖任何其他 Context，是整个领域模型的"宪法"。

AR Model

参数的集合体，由 Training 设定、Inference 读取。被 Harness 调用以生成 token。
关键属性：parameters · capability profile · knowledge cutoff
强引用：Training → Model；Inference → Model；Harness → Model

Entity Model Provider

承载 Model 的服务（Anthropic / OpenAI / Ollama / Bedrock…）。Model 的"宿主"，也是计费点。

Entity Model Provider Request

一次 Harness → Provider 的往返。是 Section 6 "Memory and Steering" 和 Section 5 "Handoffs" 的共同单位。

VO Token · Input Tokens · Output Tokens · Cache Tokens

计费与上下文的最小单位。Cache tokens 依赖 Prefix cache。

VO Effort（reasoning effort）

每条 Provider Request 的"思考时间"旋钮。

Event Next-token Prediction

不是状态，是机制——但它在所有上层实体的描述里反复出现，作为 Model 的"能力签名"。

Property Non-determinism

跨 Section 的横切关注点：Model 在 Section 4 "Failure Modes" 里再次出现，是 Hallucination / Sycophancy 的根因。

1.2 Section 2 — Sessions, Context Windows & Turns（运行时核心）

这是整个系统的运行时状态机。Session 是生命周期边界，Turn 是用户感知粒度，Context 是物理载体。三者的关系是字典里最反复强调的："Session 填满 Context Window，Turn 装一个或多个 Provider Request"。

AR Session

一次 bounded run。整个字典里最核心的聚合根——Clearing / Compaction / Handoff 都在操纵它。
内部实体：Turn[] · Message[] · ProviderRequest[] · ToolCall[]/ToolResult[]
生命周期：启动 → 累积 → 触发 Compaction/Autocompact | 用户触发 Clearing | 升级为 Handoff

AR Context Window

物理容器，模型感知的唯一表面。和 Session 是容器-内容关系（"if the context window is the box, the session is the stuff slowly filling it up"）。
内容：SystemPrompt + conversation + ToolResult[]

Entity Turn

Session 内的一次用户-代理往返。大小由 Agent 决定，不由用户决定——是 AFK 模式的基础。
层级：Session > Turn > ProviderRequest

VO Context

"agent 此刻知道什么"——抽象名词，区别于 Context Window（物理容器）和 Session（历史）。三者在原文被明确区分：context = 任务相关信息；context window = 模型看到的所有 token；session = 累积历史。

VO System Prompt

Harness 在每条 Request 上预置的指令。Prefix cache 的起点。

VO Stateless / Stateful（属性）

Section 2 的横切属性：Model 永远 stateless；Session 跨 Turn 是 stateful；Agent 跨 Session 默认 stateless，除非叠加 Memory System。Memory System 的整个存在意义就是"把 stateless 的 agent 伪装成 stateful"。

AR Agent（组合根 / DTO 性质）

Matt 原话："doesn't name a mechanical part"。它是 Model + Harness 的运行时组合，不是独立实体，而是 Section 1（Model）和 Section 3（Harness）的协作产物。

1.3 Section 3 — Tools & Environment（执行层）

Agent 唯一能"看"和"动"世界的方式。Tool 是函数接口，Environment 是数据后端，Sandbox 是安全壳，Permission 是治理层。

AR Harness （跨 Section 协调者 · S3 定义，S1/S2/S6 协作）

身份：把 stateless Model 包装成可交互 Agent 的那层软件——本身不是数据、不是参数，是"指给模型就能跑"的程序（Matt 原话："the harness is software you can point at"）。
归属：Section 3 自己定义的聚合根 AR；同时是 Section 1（Provider 调用方）、Section 2（Session 持有者）、Section 6（Memory/AGENTS.md 装载者）的协作方。不是任何单个 Section 的内部成员，是跨 Section 协调者。
职责（按 Section 归类）：
  • S1：调 Model Provider 跑 Inference（不关心 provider 内部）
  • S2：持有 Session 历史；为每条 Provider Request 装配 Context；决定何时 Compact / Autocompact；决定何时拒绝继续（context window 满）
  • S3：暴露 Tool 集合给 Model；解析并执行 Tool Call；返回 Tool Result；处理 Permission Request；通过 MCP 集成外部 Tool；挂载 Filesystem 作为默认 Environment
  • S6：Session 启动时载入 AGENTS.md 和 Memory System；维护 Skill 注册表（Progressive Disclosure）
  • 横切：提供 Effort 旋钮；维护 Prefix Cache 稳定性；处理 user 中断/注入；让 user 自定义 System Prompt 片段
它不是什么（Matt 原文边界）：
  • 不是 Model（Model 是 parameters/数据；Harness 是软件）
  • 不是 Environment（"the harness is the wrapper, the environment is the workspace"）
  • 不是 Agent（Agent 是 Model + Harness 的运行时组合视图；Harness 是其中"软件"那一半）
  • 不持久化它管理的 Session（Session 历史大多在用户机器上，不在 harness 进程内）
实例：Claude Code · Cursor · Codex CLI · Claude.ai（chat harness，不是 coding harness）
诊断价值：相同 Model + 不同 Harness = 行为可能完全不同；AI 表现不对时，先怀疑 Harness（配置、context 装配、permission），再怀疑 Model。

AR Environment

Agent 工作于其中的世界。Filesystem 是它的最常见形态，Database / API / Browser 是其他形态。
感知方式：仅通过 ToolResult 快照

Entity Tool

Harness 暴露给 Agent 调用的函数。由三部分定义：name / description / parameter schema。
实现：Built-in (Read/Write/Bash/Search) | MCP Server 提供 | 用户自注册

Event Tool Call

Model 输出的结构化文本，本身不执行任何东西——必须有 Harness 解析并执行。这是 Matt 反复强调的反直觉点。

Event Tool Result

Harness 执行 Tool Call 后回传给 Model 的结果。是 Model 感知 Environment 的唯一渠道。

AR MCP Server（外部 Context）

通过 MCP 协议向 Harness 提供 Tool 的外部进程。解决"Harness 各自集成一遍"的集成爆炸问题。
副作用：大量 Tool schema 进 Context → 必须用 Context Pointer 渐进式披露

VO Permission Mode

Agent Mode 的"闸门"切片——哪些 Tool Call 自动放行、哪些触发 Permission Request。

VO Agent Mode

Permission Mode + 注入 System Prompt 的行为指令。plan mode / accept-edits / YOLO mode 都是它的实例。

Event Permission Request

Harness 在执行非预授权 Tool Call 前向用户发的请求。可附消息 → 变成 Steering 点。

Entity Sandbox

Environment 的隔离形态（container / VM / restricted shell）。是 AFK 模式的安全前提。

1.4 Section 4 — Failure Modes（横切关注点）

这个 Section 是横切关注点集合，不是独立的运行时 Context。它解释为什么 Agent 会出错、出什么错。所有词条都把根因指向 Section 1（Model 的训练 / 推理特性）。

Event Hallucination

两种 flavor：factuality（凭空捏造）和 faithfulness（偏离载入的 context）。根因是 next-token prediction 不验证真伪。

Event Sycophancy

训练 RLHF 副作用——Model 学会"用户爱听的话"，包括附和。

VO Parametric Knowledge

Model 训练时"压进参数"的知识。Knowledge Cutoff 是它的时间戳。

VO Contextual Knowledge

通过 Tool / Memory / AGENTS.md 等外部源提供的信息。和 Parametric Knowledge 形成 Context 的内外两源。

Property Attention Budget / Degradation / Relationship

三个一组的横切属性：Context 里的 token 越多，每个 token 分到的 attention 越少。这就是 Smart Zone 现象的物理基础。

VO Smart Zone

Session 早期的高质量区间，超过约 125K–150K tokens 进入 "Dumb Zone"。规划任务的实际预算不是 context window limit，是 smart zone。

1.5 Section 5 — Handoffs（生命周期管理）

这个 Section 处理Session 怎么结束、状态怎么移交。它是 Section 2（运行时）的"出口"。

AR Handoff

把 agent context 从一个 Session 搬到另一个 Session，无返回路径。和 Subagent 的关键区别就在这里。

Event Clearing

无 transfer 的 Session 切换——新 Session 看到的是空 Context Window。Session 的"硬重启"。

Event Compaction

内存内做的 handoff：原 Session 历史被 summarize，新 Session 拿着 summary 起步。lossy by design——是 primary→secondary source 的转换。

Event Autocompact

Harness 在 Context Window 接近满时自动触发的 Compaction（典型阈值 80%）。

Entity Handoff Artifact

被作为 carry mechanism 写出来的文档。Spec / Ticket / Plan Doc 都是它的形态。

AR Spec

多 Session 工作的根 artifact。包含多个 Ticket，有 status。会随工作进展 mutate。
宿主：repo 文件 / GitHub issue / issue tracker

AR Ticket

一个 Session 工作量的 handoff artifact。可独立存在，也可挂在 Spec 下。有依赖关系（block / blocked by），形成 DAG。
大小约束：能在 Session 离开 Smart Zone 前完成 → 可测试

VO Primary Source / Secondary Source

这两个 VO 在 Section 4 (Hallucination) 和 Section 5 (Handoff) 都被引用——是字典里的认知论双胞胎：原数据 vs 派生物。

1.6 Section 6 — Memory and Steering（跨 Session 状态）

这是解决"Model + Agent 双重 Stateless"的 Context——通过 Harness 把 Environment 当外存来用。

AR Memory System

把 agent 跨 Session 伪装成 stateful 的系统。Write 路径（在 Session 中把信息落到 Environment）+ Read 路径（Session 启动时载入）。
持久层：Filesystem (e.g. Claude Code /memory 目录)
注意：Memories 自己是 secondary source，会过时，需要 prune

Entity AGENTS.md

Environment 里 Harness 在 Session 启动时自动载入的"项目对 agent 的常驻 brief"。和 Skill 的区别：每个 Session 都读，不管任务是什么。

VO Skill

可教学的 capability bundle。默认只在 Context 里放 name + description（一行），用 Progressive Disclosure 模式按需载入全文。
标准：agentskills.io；包含 SKILL.md + 可选 scripts/templates

VO Context Pointer

指向 Context 外资源的轻量引用。SKill / MCP / handoff 链回原 Session 都用它实现渐进式披露。

VO Progressive Disclosure

Section 6 的设计原则：Context 是预算，资源按需载入而不是预先全量装入。

Entity Subagent

通过 Tool Call 被 parent agent 启动的子 agent。运行在独立 Session + Context Window 里，回报单条 Tool Result。**不能继续 spawn subagent**（树深度 1）。
vs Handoff：Subagent 有返回路径；Handoff 无。Subagent 是"隔离噪声"，Handoff 是"转移阵地"

1.7 Section 7 — Patterns of Work（协作模式）

这一章是人-代理协作的工作模式目录。所有词条都在回答"人在哪里、agent 怎么工作、信心怎么保证"。

VO Human-in-the-loop（HITL）

人在 Session 中实时参与的模式。Permission Request 是它在工具层的具体实现。

VO AFK（away from keyboard）

人启动 Session 后离开的批量模式。是"AI 编程的吞吐量倍增器"。需要 Permission Mode 宽松 + Sandbox 隔离 配合。

Service Automated Check

Environment 里跑的确定性验证（test / type / lint / build / pre-commit）。确定性 by design，是 agent 能自纠错的信号源。

Service Automated Review

另一个 agent 审第一个 agent 的工作（经常换 model 或 system prompt）。non-deterministic。和 Automated Check 是两种不同的 verification layer。

Service Human Review

用户读 diff 形成判断。"读 diff 算，看 summary 不算"——summary 是 secondary source。

VO Vibe Coding

用户跳过 Human Review 的工作模式。风险随代码生命周期和 stakes 上升。

VO Design Concept（Brooks 用语）

用户和 agent 共同持有的"在建什么"的理解。Spec / 代码 / 对话都是试图捕获或抵达它的资产，都不是它本身。

Service Grilling

通过 Socratic 对话开发 Design Concept 的技巧——agent 一次只问一个决策，并提出推荐答案。

Service Prototyping

让 agent 造一个粗糙实物以提高 Design Concept 讨论保真度的技巧。当对话在某些问题上"转圈"时启用。

VO DX / AX

DX = 人类开发体验；AX = 代理开发体验。部分重叠，部分分歧。Tribal knowledge 帮助人类但对 agent 没用；漂亮 dashboard 帮人不帮 agent。

Repo Filesystem（横切存储）

最常见的 Environment。AGENTS.md / Skills / 源码 / 工具配置都住在这里。Harness "starts in your project" 就是把 agent 指向一个 Filesystem。
特性：只有 tool call 能触碰；不在 Context Window 里直到被读

2. 上下文映射图（Context Map）

下图展示 7 个 Bounded Context 之间的关系。映射符号沿用 DDD 惯例：

  • U = Upstream（上游，被依赖方）
  • D = Downstream（下游，依赖方）
  • Conformist（顺应）：下游完全接受上游模型，不翻译
  • Customer-Supplier（客户-供应）：下游需求能影响上游
  • Anti-Corruption Layer（防腐层）：下游翻译上游模型以保护自己
  • Shared Kernel（共享内核）：两个 Context 共享一部分模型
  • Open Host Service（开放主机）：上游提供协议化接口供多个下游消费

关键观察：

  1. Section 1 是宪法：所有 Section 都 Conformist 依赖它，无任何反向依赖。它是真正的 Upstream Kernel。
  2. Section 2 ↔ Section 3 互相纠缠：Agent 和 Harness 其实是同一概念的两种切面（"model in motion" vs "what turns it into an agent"），所以我把 Agent 标为跨 S2/S3 的 Shared Kernel。
  3. Harness 是跨 Section 协调者：它由 S3 自己定义（AR），但职责横跨 S1（调 Provider）、S2（持有 Session、决策 Compact/Autocompact、拒绝继续）、S6（启动时装载 AGENTS.md / Memory / 维护 Skill registry）、S7（spawn Subagent）。在 ER 图中加注 <<AR · cross-Section orchestrator>>，并新增 4 条从 Harness 出发的依赖关系（→ MemorySystem / AGENTSmd / Skill / Subagent）。
  4. Section 4 是横切层：失败模式不是独立运行时，而是对其他层的解释。虚线 + 红框标识。
  5. Section 5 是 Section 2 的出口：所有 Handoff/Clearing/Compaction 操作对象都是 Session。
  6. Section 6 = Section 2 + Section 3 的反 stateless 解决方案：Memory System 的存在完全是为了补 S2 里"Model 永远 stateless"那条规则。
  7. Primary/Secondary Source 是 S4 / S5 / S6 共享的认知论基类（标红虚线 = 横切）。

建模说明（向 Matt 的 design 致敬）
1. 7 个 Bounded Context 100% 沿用 Curriculum.md 的 Section 划分，未做合并/拆分。理由：domain.md 明确说"用 glossary 定义的词，不要自己造同义词"——Context 名也是 glossary 的一部分。
2. "Agent" 在 ER 图里被标为 <<composite role>> 而非 <<aggregate root>>，因为 Matt 原话："agent doesn't name a mechanical part"。它是 Model+Harness+Session 的运行时组合视图，不是独立实体。
3. 横切关注点（Non-determinism / Attention* / Smart Zone / Primary/Secondary Source）用红色虚线标识——它们在原词条里也被描述为"贯穿多个 Section 的属性"。
4. Hallucination / Sycophancy 被建模为 <<event>> 而非 entity，因为它们是"已经发生的事实"，不是"需要维护的状态"。
5. Harness 是个特例：它是 Section 3 自己定义的聚合根 AR，但同时协调 S1（Provider 调用）、S2（Session 持有 + Compact 决策）、S6（AGENTS.md / Memory / Skill 装载）、S7（Subagent 派生）。在 ER 图里标为 <<AR · cross-Section orchestrator>>，比单一 AR 多了一条"跨 Section 协调者"的标签。Matt 原文用 5 个不同动词（assembles / executes / stores / asks / decides）列出 Harness 职责，分布确实横跨 4 个 Section——这在字典里没有其他词条是这样。
