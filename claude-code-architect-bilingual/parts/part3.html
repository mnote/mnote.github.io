Skills, the subject of Part Two, taught Claude how to do specific kinds of work consistently. They are an answer to the question of capability. The chapters that follow are about a different question, and a different answer. The question is what to do when work that needs to happen in a single session crosses several different kinds of attention, when the context window starts filling with material that the current task does not need, when the developer wants three things investigated at once instead of one, and when the cognitive cost of switching modes inside a single Claude session begins to degrade the quality of every output. The answer to these problems is the second pillar of the framework, the subagent.
第二部分讲的 Skills,教的是 Claude 如何稳定地做好某一类具体工作——它回答的是"能力"的问题。接下来的几章,问的是一个不同的问题,也给出一个不同的答案。当一个 session 里的工作横跨好几种"注意力类型"、当上下文窗口开始被与当前任务无关的内容塞满、当开发者希望三件事并行调研而不是一件一件来、当"在同一个 Claude session 里反复切换模式"所产生的认知代价开始让每一条输出都降级时,该怎么办?这些问题的答案,就是框架里的第二柱——subagent(子代理)。
Begin with a definition that will guide every chapter in this part of the book. A subagent is a separate Claude process, with its own system prompt, its own restricted set of tools, and its own isolated context window, that the main session can dispatch to perform a specific kind of work. When the subagent finishes its work, only its final output returns to the main session. The dozens of tool calls the subagent may have made along the way, the files it may have read, the drafts it may have considered, the dead ends it may have explored, none of that enters the main session. The main session sees a clean result, and the work that produced the result happens in a parallel space that the main session never has to see.
先给一个定义,后续每一章都会用到它。一个 subagent 是一个独立的 Claude 进程——它有自己的 system prompt、自己受限的工具集、自己隔离的上下文窗口——主 session 可以把它派出去,执行某一类特定的工作。subagent 完成工作之后,只有它的最终输出会回到主 session 之中:子代理一路调过的几十个工具、看过的文件、考虑过的草稿、走过的死胡同,这一切都不会进入主 session。主 session 看到的只是一份干净的结果;真正产出这份结果的工作,发生在主 session 永远不必看见的"平行空间"里。
This is a substantial architectural commitment. To understand why the commitment is worth making, it is worth examining what happens to a Claude Code session that does not use subagents and that is asked to do something complex. Take a real example. A developer asks Claude Code to add a new feature to a substantial codebase. The work involves understanding the existing architecture, designing the new addition, writing the code, writing tests for it, updating documentation, and reviewing the whole change for quality. A single Claude Code session can do all of these things in sequence, and it often does. But there is a hidden cost.
这是一项相当重的架构承诺。要理解这个承诺为什么值得付出,值得先看看:当一个 Claude Code session 不使用 subagent、却被要求做一件复杂的事时,会发生什么。举一个真实的例子:开发者让 Claude Code 给一个相当规模的代码库加一个新功能。这件工作包括:理解现有架构、设计新增内容、写代码、给它写测试、更新文档、再对整组改动做一遍质量评审。一个 Claude Code session 完全能按顺序把这些事做完,而且它经常就是这样做的。但这里有一个隐性的代价。
In the first phase, Claude reads many files to understand the existing architecture. Each file Claude reads adds to the context window. The context grows by hundreds or thousands of tokens for every file. By the time Claude has built a working understanding of the architecture, the context window is full of source code, much of it only loosely relevant to the new feature.
在第一阶段,Claude 要读很多文件,以理解现有架构。每读一个文件,上下文窗口就多一份内容——每多一个文件,就多几百到几千 token。等到 Claude 真的把架构"读到能上手"的时候,上下文窗口里已经堆满了源代码,而且其中相当一部分只是松散地和新功能相关。

In the second phase, Claude designs the new addition. The design involves several false starts, each of which leaves traces in the context. By the third phase, when Claude is writing the actual new code, the context window contains the architectural exploration, the design exploration, and the writing of the new code, all jumbled together. By the time Claude reaches the test-writing phase, the context window is dominated by historical material that has nothing to do with testing, and the test-writing suffers as a result, because the model is trying to write tests while looking at the residue of three earlier phases of work.
到了第二阶段,Claude 开始设计新增内容。设计过程会经历几次"试错回头",每一次都会在上下文里留下痕迹。等到第三阶段,Claude 真正开始写代码时,上下文窗口里已经同时装着"架构探索"、"设计探索"和"新代码写作"——三件事搅在一起。再到"写测试"这一阶段,上下文窗口里占主导的已经变成与测试毫无关系的"历史残渣";而写测试这件事,也就因此受了影响——模型是一边盯着前三个阶段留下的残渣,一边在写测试的。

The Failure Mode Subagents Prevent · subagent 要防止的失败模式

This is the failure mode that subagents exist to prevent. The architecture of a subagent is a direct response to this problem. Each subagent has its own context window. The architectural exploration happens inside an explore subagent, whose context fills with the relevant source code, but only the subagent's final summary returns to the main session. The main session never has to see the dozens of files the subagent read. When the main session moves on to design, it does so with a clean context that contains the summary, not the exploration. When the main session moves on to test writing, the design exploration similarly never enters its context, because the design happened in another subagent. Each phase of work happens in a context that is appropriately scoped to that phase, and the main session preserves a clean overview of the whole project rather than becoming a clearinghouse for every detail of every phase.
这就是 subagent 之所以存在的失败模式。subagent 的架构,正是对这个问题的一种"直球"回应:每个 subagent 都拥有自己的上下文窗口。"架构探索"这件事发生在一个 explore subagent 里——它的上下文会被相关源码填满,但只有它最终的摘要会回到主 session。主 session 根本不必看见那个 subagent 读过的几十个文件。主 session 进入设计阶段时,带着的是一份干净、只含"摘要而非探索过程"的上下文。进入写测试阶段时,"设计阶段的探索"也同样不会进它的上下文,因为设计发生在另一个 subagent 里。每一阶段的工作,都发生在一个恰好匹配该阶段的上下文里;而主 session 始终保持着一份对整个项目的"干净概览",不至于变成"每个阶段每处细节的总收发室"。
Three properties of subagents follow from this architecture, and they are worth naming because every subagent design decision later in this part of the book is a function of one of these three properties.
从这套架构自然引出 subagent 的三条属性。值得给它们取个名字——本部分后面每一个 subagent 的设计决策,都不过是这三条属性中某一条的函数。
The first property is context isolation. The subagent's context is its own. The main session cannot see what the subagent is reading. The subagent cannot see what the main session is doing in parallel. The two communicate only through the subagent's initial brief and the subagent's final result. This isolation is the source of subagents' context-saving power, but it is also a constraint the developer needs to design around. A subagent cannot be told something halfway through its work; whatever it needs to know must be packed into the brief that launches it.
第一条属性是上下文隔离(context isolation)。subagent 的上下文是它自己的。主 session 看不见 subagent 在读什么;subagent 看不见主 session 在并行做什么。两者只通过两件事通信:启动时的 brief 和最终结果。这种隔离既是 subagent 能"省上下文"的力量之源,也是一个开发者必须围绕其做设计的约束——你没法"中途"告诉 subagent 什么新信息;它需要知道的一切,都得在启动它的 brief 里就打包好。

The second property is specialization. A subagent has its own system prompt, distinct from the main session's system prompt. The system prompt establishes the subagent's role, its expertise, its style of thinking, its outputs. A code-reviewer subagent has a system prompt that is tuned for the craft of reviewing code, not for the broader job of being a general programming assistant. A test-writer subagent has a system prompt that is tuned for the craft of writing tests. The narrowness of the system prompt is a feature, not a limitation. A specialist who is asked to do only one kind of work, and who has been briefed in detail about how to do that work well, produces consistently better outputs than a generalist who is asked to do everything.
第二条属性是专门化(specialization)。subagent 拥有自己的 system prompt,且和主 session 的 system prompt 截然不同。这份 system prompt 确立 subagent 的角色、专长、思考风格、产出形态。一个 code-reviewer subagent 的 system prompt,是围绕"代码评审这门手艺"调出来的,而不是围绕"当一个通用编程助手"调出来的;一个 test-writer subagent 的 system prompt,是围绕"写测试这门手艺"调出来的。system prompt 的窄,是一种特性,不是限制——被指派只做一类事、并被详细交代过"如何把这事做好"的专员,产出的稳定质量,会高于"什么都做"的通才。
The third property is parallelism. Multiple subagents can run at the same time. Claude Code can run several subagents concurrently; community guidance from Anthropic engineers and from heavy users converges on roughly ten as a practical ceiling before queueing becomes noticeable, although the exact number is environment-dependent and Anthropic has not published a hard cap. This means that work which is genuinely independent can happen in parallel rather than in sequence. A code review that involves a security pass, a performance pass, a style pass, and a test-coverage pass does not have to be four sequential reviews. It can be one parallel review where four subagents work simultaneously and the main session synthesizes their findings when they all return. The wall-clock time savings are substantial. The quality improvements are also substantial, because each subagent is focused on its own dimension and does not have to balance attention across all four.
第三条属性是并行(parallelism)。多个 subagent 可以同时跑。Claude Code 能并发跑若干个子代理;来自 Anthropic 工程师和重度用户的社区经验大致收敛在"十个左右"——超过这个数,排队的延迟就开始能被感知;当然具体数字因环境而异,Anthropic 也没有公开过一个硬上限。这意味着:真正独立的工作,完全可以并行发生,而不是顺序发生。一次代码评审,要做"安全"、"性能"、"风格"、"测试覆盖"四道扫描——它不必是依次发生的四次评审,而可以是并行的一次评审:四个 subagent 同时工作,主 session 等它们都返回后再做综合。挂钟时间上的节省相当大;质量上的提升也相当大——因为每个 subagent 都在自己的维度上保持专注,不必把注意力在四个维度间来回分配。

Where Subagents Live · subagent 住在哪里

Where do subagents live, mechanically? They live as files in the .claude/agents directory. Project-level subagents live at .claude/agents in the root of a specific project, where they apply only inside that project. User-level subagents live at ~/.claude/agents in the user's home directory, where they apply across every project. The naming convention is the same as for skills: lowercase, hyphenated, descriptive. Each subagent is a single Markdown file with YAML frontmatter at the top and a system prompt body below. Here is the simplest possible subagent definition, complete and ready to install.
subagent 在"机械层面"住在哪里?它们以文件形式住在 .claude/agents 目录里。项目级 subagent 放在某个项目根目录下的 .claude/agents,只在那个项目里生效。用户级 subagent 放在用户家目录的 ~/.claude/agents,跨所有项目生效。命名约定和 skill 一样:小写、连字符、具描述性。每个 subagent 就是一个 Markdown 文件,顶部是 YAML frontmatter,下面是 system prompt 主体。下面是"最小可用的 subagent 定义",完整、可以直接装上。

Look closely at this file, because every subagent in the rest of this part of the book follows the same shape. The frontmatter has four fields, two of which are required. The name field is the subagent's identifier and must match the filename. The description field is what tells Claude when this subagent should be dispatched, and it is the subagent equivalent of the skill description; the same craft of trigger writing applies. The tools field, optional, restricts the tools available to the subagent. The model field, also optional, lets the developer choose which model the subagent runs on, which matters because heavier work might warrant the strongest model while lighter work can use a faster one.
请仔细看这个文件——本部分后面出现的每一个 subagent,都是这个形状。frontmatter 一共四个字段,其中两个是必填。name 字段是 subagent 的标识,必须和文件名一致。description 字段告诉 Claude"什么时候该派这个 subagent",它相当于 subagent 版的 skill description——trigger 的写法工艺同样适用。tools 字段是可选的,用来限制 subagent 可用的工具。model 字段也是可选的,让开发者选 subagent 跑在哪个模型上——这一点之所以重要,是因为"重活"值得用最强的模型,而"轻活"可以用更快的那个。

Reference specific file paths and line numbers in your feedback. Keep the review focused: a short, sharp review is more useful than a long padded one.
The body of the file is the subagent's system prompt. It is read every time the subagent is dispatched, and it shapes everything the subagent does. The body of a subagent is, in this respect, more consequential than the body of a skill, because while a skill body adds instructions to the main session's overall behavior, a subagent body becomes the entire personality of a separate Claude process. The development of this body is the subject of the next chapter, and it is where the most important design decisions for any subagent get made.
文件的正文,就是 subagent 的 system prompt。每次 subagent 被派出去,这份 system prompt 都会被读入,并塑造它接下来做的所有事。从这个意义上说,subagent 正文的影响,要大于 skill 正文的影响——因为 skill 正文只是给主 session 的整体行为"追加一些指令";而 subagent 正文,会成为另一个 Claude 进程的整体人格。这份正文怎么写,正是下一章的主题——也是任何一个 subagent 最重要的设计决策所在。
Two conventions concerning invocation are worth knowing now. The first is automatic delegation. When the main session is working on a task and notices that one of the available subagents has a description matching the work, the main session can delegate to that subagent on its own initiative. The developer does not need to type any special command to invoke the subagent; she simply describes her task, and the main session decides whether the task should be handled in-line or delegated. This is the same principle that governs skill firing, applied to a different mechanism.
关于"调用",有两条约定值得现在就了解。第一条是自动委派(automatic delegation)。主 session 在处理任务时,如果注意到"可用的 subagent 中,某条的 description 匹配当前工作",主 session 就会自主把它派出去。开发者不需要敲任何特殊命令来"召唤" subagent——她只要把任务用自然语言说清楚,主 session 就会自己决定:这件事是就地做,还是委派给某个 subagent。这套原理和"skill 何时触发"是一样的,只是套在了一个不同的机制上。
Good descriptions cause appropriate delegation. Weak descriptions cause subagents to sit unused.
好的 description 会带来恰当的委派;弱的 description 会让 subagent 一直闲坐。

The second convention is explicit invocation. The developer can also invoke a subagent directly, by typing @agent-name in the prompt. The mention triggers the named subagent immediately, with whatever brief follows in the prompt as the dispatch instructions. Explicit invocation is useful when the developer wants to be sure a particular subagent handles a particular task, when the description-based delegation might not fire reliably, or when the developer wants to compose multiple specific subagents on a single task. Both invocation modes are valid, and most working developers use both, depending on the situation.
第二条约定是显式调用(explicit invocation)。开发者也可以直接在 prompt 里敲 @agent-name 来"点名"某个 subagent。这一提,会立刻触发被点名的 subagent,而 prompt 中跟在后面的内容,就是派给它的 brief。显式调用在以下场景特别有用:你希望"某个 subagent 一定要处理某件事"、"靠 description 的委派不够稳"、"你想把多个具体 subagent 组合到一件事上"。两种调用方式都成立——多数实际用起来的开发者会两种都用,看场景挑一种。

Automatic Versus Explicit · 自动 vs 显式

The relationship between automatic delegation and explicit invocation is worth a moment of attention, because choosing between them is a real design question. Automatic delegation is convenient. The developer types in plain language and the right specialist is dispatched, much as the right skill is fired. The cost of automatic delegation is reliability. Description-based dispatch is a judgment call that the main session has to make for every prompt, and the call can occasionally be wrong, especially when several subagents have overlapping descriptions. Explicit invocation is reliable. The developer names the subagent she wants and the subagent runs, full stop. The cost of explicit invocation is friction. The developer has to remember the subagent's name and choose to type it. A working pattern that develops in most experienced users is a hybrid: explicit invocation when the work is high-stakes and the developer wants certainty about which specialist runs, automatic delegation when the work is routine and the convenience matters more than the certainty. The hybrid produces the best of both, and it is worth deliberately practicing both invocation modes during the first weeks of subagent use.
"自动委派"和"显式调用"的关系,值得花片刻讲清楚——因为在两者之间做选择,其实是一个真正的设计问题。自动委派很方便:开发者用日常语言敲下去,合适的专员就被派出,和 skill 的"对的 skill 自动触发"差不多。代价是可靠性:基于 description 的派单,是主 session 在每个 prompt 上都要做的一次判断,而这个判断偶尔会出错——尤其是当多个 subagent 的 description 互相重叠的时候。显式调用很可靠:你点名哪个 subagent,就是它,全无歧义。代价是摩擦:开发者得记得那个 subagent 的名字,并且主动把它敲出来。大多数熟练用户最后会形成一种"混合"模式:高风险工作、要确定是哪位专员跑的,显式调用;常规工作、便利比确定性更重要的,自动委派。这种"混合"兼具两者之利,在开始用 subagent 的头几周里,值得有意识地两种都练一练。
A note on the relationship to skills. Skills and subagents address different problems and complement each other rather than competing. A skill teaches Claude how to do a specific task well. A subagent provides a separate context and a specialized role for a kind of work. Many sophisticated workflows use both: a subagent handles a kind of work, and inside the subagent, skills fire when relevant tasks come up during that work. A test-writer subagent might activate a project-specific test-conventions skill at the moment it begins drafting tests. The two systems compose, and the composition is where the deepest leverage of Claude Code begins to surface. Chapter Fourteen is dedicated entirely to this composition.
再说说和 skill 的关系。Skill 和 subagent 解决的是不同的问题,二者是互补而不是竞争。Skill 教 Claude 如何把一件具体的事做好;subagent 则为某一类工作提供一个独立的上下文和一个专门的角色。许多成熟的工作流会把两者都用上:subagent 负责某一类工作,在它"里头"工作展开时,相关的 skill 又会在该触发的时刻被触发。比如一个 test-writer subagent 在它开始起草测试的那一刻,可能会激活"项目专属测试规约"这个 skill。两套系统是可组合的;而这种组合,才是 Claude Code 最深杠杆的起点。第十四章整章都会讲这种"组合"。

A short clarification for readers who have come from a background of writing prompts and may be confused about why subagents are not simply elaborate prompts. The difference is real and structural. A prompt, no matter how elaborate, runs in the same context as everything else in the session. The context window is shared. The system prompt is shared. A subagent has a separate process, a separate context, and a separate system prompt. The architectural distinction matters because it produces different behavior. A prompt cannot stop the rest of the session from polluting its context. A subagent runs in a clean slate. This is not a difference of degree. It is a difference of kind, and developers who try to replicate subagent benefits with cleverer prompts inside a single session will find that the benefits do not survive the lack of architectural separation. The right answer is to use the architecture, not to try to simulate it.
对那些"来自 prompt 写作背景"的读者,这里要做一个简短的澄清——你可能困惑:为什么 subagent 不就是"复杂版的 prompt"呢?这个区别是真实且结构性的。一个 prompt,无论写得多复杂,都和 session 里的其他东西跑在同一个上下文里——上下文窗口是共享的,system prompt 是共享的。一个 subagent 则拥有独立的进程、独立的上下文、独立的 system prompt。这个架构上的差异之所以重要,是因为它会直接造成不同的行为。一个 prompt 挡不住 session 其他部分去"污染"它的上下文;而一个 subagent 跑在干净的白纸上。这不是程度上的差别,而是类型上的差别——想用"更聪明的 prompt"在同一个 session 里模拟 subagent 收益的开发者,会发现那份收益根本撑不住:没有架构上的隔离,收益也就不在了。正解是用架构,而不是模拟架构。
A short word on the relationship to Claude Code's built-in subagents. Three subagents ship with Claude Code by default and are present in every session: Explore, Plan, and General-purpose. Explore is read-only and runs on Haiku by default; it is optimized for quickly searching and understanding a codebase without making changes. Plan gathers context before the main session enters plan mode, where a strategy is presented. General-purpose handles tasks that need a mixture of exploration and modification. The developer does not invoke these directly very often; the main session routes work to them automatically. Their existence is worth knowing because they are a useful proof of concept of the subagent architecture and because, when the developer designs her own custom subagents, she is extending a system that Anthropic itself uses every day.

It is worth examining the cost side of subagents honestly, because the architecture has trade-offs that the developer should understand before building a heavy subagent library. The Cost and Its Compensation · 成本与它的补偿

The compensation for this cost is significant, and it has two components. The first component is the quality improvement that comes from a clean, focused context. A subagent producing a security review in a context that contains only a security-review system prompt and the relevant code will produce a deeper review than a main session that is also juggling architectural decisions, build configuration, and three previous tasks. The quality difference is usually worth more than the token cost, because the developer's time is the scarce resource, not the tokens. The second component is the wall-clock saving from parallelism, which only applies in multi-subagent workflows. When four subagents run simultaneously, the wall-clock time is determined by the slowest of the four, not by the sum. The token cost is roughly four times higher than the equivalent sequential work, but the time cost is one quarter, and time is the dimension that governs how many tasks the developer can complete in a working day.
对这份成本,有两份"补偿",分量都不轻。第一份是来自"干净、专注的上下文"的质量提升。一个 subagent,做安全评审,而它的上下文里只有"安全评审 system prompt + 相关代码",它产出的评审深度,会高于"主 session 同时还忙着架构决策、构建配置、上一二三件事"的那种情形。这种质量差距,通常比 token 成本本身更值——因为真正稀缺的资源是开发者的时间,而不是 token。第二份是来自并行的挂钟时间节省——它只在多 subagent 工作流里奏效。四个 subagent 同时跑,挂钟时间由其中最慢的一个决定,而不是四者之和。token 成本大约是"等价串行工作"的四倍,但时间成本是四分之一;而"一个工作日里能完成多少任务",正是由时间这个维度决定的。
A balanced view, then, is that subagents are worth dispatching when context isolation matters, when specialization is possible, when parallelism applies, or when several of these are true at once. Subagents are not worth dispatching when the work is small, when the main session's context is already clean, and when no specialization or parallelism is available. The developer who internalizes this balanced view will reach for subagents at the right moments and refrain from over-dispatching them at moments where they would only add overhead.
一个平衡的看法是:在以下场景里,subagent 值得派出——上下文隔离重要、专门化可能、并行适用,或三者同时成立;在以下场景里,subagent 不值得派出——工作很小、主 session 的上下文已经干净、且没有可用的专门化或并行。把这个"平衡看法"真正内化的人,会在对的时刻伸手召唤 subagent,也会在该收手的时刻克制自己——不至于在那些 subagent 只会徒增开销的场合,过度派单。
A second balanced view concerns the human side of subagent use. Some developers, on first encountering subagents, become enthusiastic and try to dispatch them on every task. The result is sometimes slower than the work would have been without them, because the orchestration overhead exceeds the benefits. Other developers, on first encountering subagents, treat them with suspicion and avoid them entirely. The result is that they never benefit from the architecture and continue to operate inside an increasingly polluted main session. Both extremes are mistakes. The right relationship with subagents, after a few weeks of practice, becomes intuitive: the developer reaches for them when the task has an obvious specialization or parallelism shape, and lets the main session handle the rest. This intuition is not difficult to develop, but it requires a few weeks of deliberate use to settle in. The reader who works through Part Three patiently will arrive at the intuition without having to think about it explicitly any longer.
第二个"平衡看法",是关于人使用 subagent 时的心智层面。开发者第一次接触 subagent 时,有些会变得热情高涨,恨不得每个任务都派——结果有时反而比不派还慢,因为"编排开销"大于收益。也有些开发者第一次接触 subagent 时,满腹狐疑,干脆一个都不用——结果就是他们从来享受不到这套架构的好处,继续在"越来越被污染的主 session"里工作。两个极端都是错的。和 subagent 的正确关系,经过几周实操,会变成一种直觉:遇到任务天然具有"专门化或并行"的形状,就会伸手召唤;其余的事,放给主 session 处理。这种直觉并不难养成,但确实需要几周有意识的练习,才能"安定下来"。耐心走完第三部分的读者,会自然而然地获得这种直觉,不再需要时刻把它挂在嘴边。

CHAPTER ELEVEN · 第十一章
Designing Effective Subagents: Role, Tools, and Boundaries
设计高效的子代理:角色、工具与边界

"Give a person too much to do, and they do nothing well. Give them one thing, and they may surprise you." — Peter Drucker, paraphrased
"给一个人太多事,她什么也做不好。只给她一件事,她可能给你惊喜。" —— 彼得·德鲁克(转述)
A subagent that does too much is worse than no subagent at all. This sounds counterintuitive on first hearing, because the natural instinct of a developer encountering a new capability is to put as much capability into it as possible. The instinct is wrong, and this chapter explains why and what to do instead. The art of subagent design is the art of restraint. The subagent that performs one role well, with a tightly defined scope and a thoughtfully constrained set of tools, produces consistent, reliable, useful output. The subagent that tries to be a general assistant in a slightly different costume produces output that is sometimes excellent, sometimes mediocre, and almost never reliably one or the other. Reliability is the entire point.
一个"做太多"的 subagent,比"没有 subagent"更糟。这话初听像是反直觉——因为开发者面对一项新能力时,本能反应就是把尽可能多的能力塞进去。这个本能是错的。本章会解释它为什么错,以及正确做法是什么。Subagent 设计的艺术,本质是克制的艺术。一个把单一角色做好、范围严格、工具精心收窄的 subagent,产出是稳定、可靠、可用;一个"换了一身衣服的通用助手"型 subagent,产出偶尔精彩、偶尔平庸,而且几乎从来不会稳定地只属于其中一种。可靠性,就是全部意义所在。
Three design dimensions govern every subagent, and the disciplined consideration of each is what separates good subagents from poor ones. The first dimension is role. The second is tools. The third is boundary. Each of these expresses a constraint, and constraints are what make subagents useful. A subagent without constraints is, in effect, a slightly more isolated version of the main session, and most of the value of having a subagent is forfeited.
三个设计维度决定每一个 subagent 的好坏——对每一个维度"有纪律地思考",正是好与差的分水岭。第一个维度是角色(role),第二个是工具(tools),第三个是边界(boundary)。三者各表达一种约束——而约束,正是 subagent 之所以有用的原因。一个没有约束的 subagent,说穿了只是"主 session 的稍隔离版本";拥有 subagent 的大半价值,会在这种设计里被浪费掉。
Begin with role. The role of a subagent is its identity, expressed at the top of its system prompt. A code-reviewer subagent is a code reviewer. Not a general programmer who reviews code sometimes. Not a teacher who happens to be reviewing code. A code reviewer. The role definition should be specific enough that it constrains the kind of work the subagent does, the kind of language it uses, the kind of judgment it brings, and the kind of output it produces. A weak role definition reads like a job title. A strong role definition reads like the introduction of a person.
从角色说起。subagent 的角色,就是它的"身份",写在 system prompt 的最前面。一个 code-reviewer subagent,就是一位代码评审者——而不是一位"偶尔评审代码的通用程序员",也不是一位"恰好在做评审的老师"。它就是代码评审者。角色定义要足够具体,具体到:它能约束这个 subagent 做什么类型的工作、用什么类型的语言、做哪种判断、产出什么形态的输出。弱的角色定义,读起来像一行岗位名;强的角色定义,读起来像一个人的开场介绍。

Move to tools. The tools field in the frontmatter restricts which tools the subagent is allowed to invoke. Omitting the field grants the subagent the full set of tools available to the main session. Specifying a list narrows the set. The narrowing is not a security feature alone, although it is a useful one. The narrowing is also a focusing feature. A subagent that has only the tools it needs does not get distracted by the tools it does not need. A code-reviewer subagent that has access only to Read, Grep, and Glob cannot make file edits even if its system prompt forgets to forbid them, and the absence of Edit, Write, and Bash from its toolkit shapes how it approaches every task. 接下来说工具。frontmatter 里的 tools 字段,用来限制 subagent 可以调用哪些工具。不填这个字段,subagent 就拿到主 session 的全套工具;填上列表,工具就被收窄。收窄,不仅仅是一个安全特性(虽然它确实有用)——它更是一个聚焦特性。一个只拥有"它真正需要的工具"的 subagent,不会被"它不需要的工具"分心。一个只拥有 Read、Grep、Glob 的 code-reviewer subagent,即使 system prompt 忘了写"不许改文件",它也改不了——因为 Edit、Write、Bash 根本不在它的工具箱里,这份"不在"塑造了它对待每一项任务的方式。它不会随口提议"顺手把它发现的问题修了",做不到,工具不在,于是它的输出自然就反映了这条边界。
A simple rule guides tools restriction. Begin with no tools, then add only the ones the subagent demonstrably needs. A reviewer needs to read files, search them, and find them, so Read, Grep, and Glob suffice. A documentation-writer needs to read files and write new ones, so Read, Write, and Glob suffice. The principle in each case is that the tool list mirrors the subagent's job description. If the subagent does not need a tool to do its job, the tool is not granted, full stop.

Move to boundary. The boundary of a subagent is the set of things it explicitly does not do. The role definition says what the subagent is. The boundary says what the subagent is not. 这样用心设计出来的 subagent,在多次调用间会产出惊人地一致的输出。两位不同的开发者,把同一个 subagent 跑在两个不同的代码库上,会拿到"看起来像出自同一位安全工程师"的报告——因为在有意义的层面上,本来就是同一位。这种一致性,正是 subagent 之所以能成为"更大系统的组件"的原因。输出每次大变的 subagent,很难和其他 subagent 组合、很难复盘、也很难被信任;输出形态稳定(只是内容随代码库而变)的 subagent,可以放心地嵌入到更大的工作流里。

Your principles:
- Documentation explains why, not what. Anyone can read the code to see what it does. Documentation should explain why it does that, what trade-offs were made, and what assumptions hold.
- The audience is a smart engineer who has not seen this code before and who will spend roughly five minutes deciding whether to read further. Calibrate accordingly.
- Examples beat prose. A short worked example is worth several paragraphs of explanation.
- Honest documentation beats aspirational documentation. Document what the code actually does today, not what you wish it did.
- Concise documentation is read. Long documentation is skimmed at best and ignored at worst.

Your method:
1. Read the code in full. Read the surrounding code if needed for context.
2. Identify the public surface of the code: what callers will use.
3. Produce documentation in the project's existing format. Inspect the project to determine what format is in use (README, JSDoc, Sphinx, etc.).
4. Cover, in order: purpose, public API, expected inputs and outputs, important behaviors and edge cases, a short worked example, any non-obvious considerations.

What you do not do:
- You do not modify code. Your edits are confined to documentation files.
- You do not write documentation that is a transliteration of the code into English.
- You do not invent behaviors that the code does not exhibit.
- You do not pad. A short, accurate page is the goal.
- You do not produce sycophantic prose. Avoid phrases like "powerful," "elegant," or "robust" unless the developer would say them in plain conversation.

A Debugging Lesson · 一条调试心得

The lesson the developer took away from this debugging session was that subagent quality is largely controlled by the specificity of the instructions in the system prompt. A subagent given vague instructions produces vague work. A subagent given specific, structured instructions, with explicit prohibitions on the failure modes the developer has already encountered, produces work that consistently lives up to the design. The fix is rarely to make the subagent smarter. The fix is almost always to make the instructions more specific.
这位开发者从这次调试里带走的心得是:subagent 的质量,几乎完全由"system prompt 里指令的具体程度"决定。给一份含糊的指令,得到的是含糊的产出;给一份具体、有结构、且对"已经踩过的失败模式"有显式禁止的指令,产出就能稳定地配得上设计者的预期。修法的方向很少是"让 subagent 更聪明",几乎总是"让指令更具体"。
A final practice deserves mention before this chapter ends, because it is the practice that separates careful subagent design from sloppy subagent design. After writing a subagent, the developer should test it on three different inputs and compare the outputs. Not for correctness, although correctness matters. For consistency. The three outputs should look like they came from the same specialist. Same format. Same tone. Same level of detail. If the outputs vary in any of these dimensions, the system prompt has not pinned down the relevant degree of freedom, and the system prompt should be tightened until the variation disappears. This three-input test takes ten minutes and prevents an entire category of long-tail problems that would otherwise only surface in a real session at an inconvenient moment.

A short reflection on the role of the model field in subagent design. The model field in the frontmatter lets the developer specify which model the subagent runs on. This may seem like a minor detail, but in practice it is one of the more consequential design choices. Subagents that demand the strongest reasoning, such as the security-auditor and the architecture-reviewer earlier in this part of the book, benefit from running on opus. Subagents that perform fast pattern-matching work, such as a search-helper or an explore agent, can run on haiku and complete in seconds rather than minutes. The model field, used thoughtfully, lets the developer tune each subagent to the cost and speed profile that best fits its job, rather than running everything on a single model and either overspending on simple work or underspending on demanding work. CHAPTER TWELVE · 第十二章
Parallel Subagents and the Orchestrator Pattern
并行子代理与编排者模式

"Coordination is the art of getting many things done in the time of one. The conductor does not play any of the instruments." — Folk wisdom of the orchestra pit
"协调的艺术,就是让许多件事在"一件事的时间里"做完。指挥家自己不演奏任何一种乐器。" —— 乐池里流传的民间智慧
The previous chapter taught the design of a single subagent. This chapter is about what happens when multiple subagents work on the same task at the same time. Parallelism is the property that turns subagents from a useful refinement into a structural change in how a developer relates to her tool. A single subagent saves context. Multiple parallel subagents save wall-clock time, deepen quality through specialization, and produce reviews and analyses that no single Claude session, no matter how capable, could produce in the same span of minutes.
上一章讲的是"单个 subagent"的设计。本章讲的是"多个 subagent 同时做一件事"时会发生什么。并行(parallelism)这条属性,把 subagent 从"一项有用的精修"变成"开发者与她工具之间关系的结构性改变"。一个 subagent 节省上下文;多个并行 subagent 节省挂钟时间、通过专门化深化质量、并产出那种"任何单个 Claude session、再怎么强,也不可能在同一段分钟数里做出"的评审与分析。
Begin with the simple case. The main session is asked to perform a task that has multiple genuinely independent components. The components do not need to share information with each other, and the order in which they are performed does not affect the result. A code review of a substantial pull request is a perfect example. A reviewer worth her salt will check several dimensions: correctness, security, performance, style, test coverage. None of these dimensions strictly depends on any other. A correctness check does not need the security check to have run first. A style check does not need the performance check to be complete. The dimensions are orthogonal, which is exactly the property that makes them candidates for parallel execution.
先看最简单的那种情形:主 session 接到一项任务,任务包含若干个真正独立的组件。这些组件之间不需要共享信息,执行顺序也不影响结果。一次对大型 PR 的代码评审,就是个完美例子。一名有分量的评审者会从几个维度去查:正确性、安全、性能、风格、测试覆盖。这些维度之间没有严格的依赖关系——正确性检查不需要等安全检查先做完,风格检查也不需要等性能检查先完成。各维度是正交的——这种正交性,恰恰是它们适合被并行执行的原因。
The orchestrator pattern formalizes the idea. The main session takes the role of conductor. It receives the task, decomposes it into independent components, dispatches one subagent per component, waits for them all to finish, and synthesizes their outputs into a unified result. The subagents do not speak to each other. They do not know about each other. Each one focuses on its single dimension, produces its single bounded report, and returns. The conductor takes all the reports, weaves them together according to whatever format the unified output requires, and presents the result to the developer. The developer sees one coherent answer. The work that produced the answer happened in parallel, in five separate contexts, each tuned to its own dimension.
编排者模式(orchestrator pattern)把这个想法形式化。主 session 担任指挥家角色:它接下任务,把它拆成若干个独立组件,为每个组件派一个 subagent,等它们全部跑完,再把它们的输出综合成一份统一结果。subagent 之间互不说话、互不知道彼此。每个 subagent 都聚焦于自己的那一维,产出自己那份边界清晰的报告,然后返回。指挥家把所有报告收齐,按"统一输出所需的格式"编织成一份,再交给开发者。开发者看到的是一份连贯的答案;而这份答案背后发生的工作,是并行发生的——发生在五个相互独立、各自针对自己维度的上下文里。

A worked example will make this concrete. The developer has a pull request she wants reviewed thoroughly before merging. She types into Claude Code something like, give me a full review of this PR, including security, performance, style, and test coverage. The main session recognizes that a thorough review is being requested, recognizes the dimensions involved, and dispatches four subagents in parallel: a security-auditor, a performance-reviewer, a style-reviewer, and a test-coverage-checker. Each subagent receives the same brief: review this diff, focused on your dimension. Each subagent runs in its own context, reads the relevant files, applies its specialty, and produces its bounded report. The four reports return to the main session. The main session presents them in a unified format, with a summary judgment that integrates the findings across the four dimensions.
一个完整例子会让这件事更具体。开发者有一个 PR,想在合并前被彻底评审一遍。她在 Claude Code 里敲一句类似的话:"给我一个完整的 PR 评审,覆盖安全、性能、风格、测试覆盖。"主 session 识别出"用户要的是一次彻底评审",识别出里面涉及的维度,于是并行派出四个 subagent:security-auditor、performance-reviewer、style-reviewer、test-coverage-checker。每一个 subagent 收到的 brief 都一样:评审这份 diff,聚焦于你负责的维度。每个 subagent 跑在各自的上下文里,读相关文件,发挥自己专长,产出边界清晰的报告。四份报告回到主 session;主 session 用统一格式呈现它们,并给出一段"把四维发现整合在一起"的总结判断。

Estimating the Wall-Clock Saving · 估算挂钟时间的节省

The wall-clock saving is straightforward to estimate. If each subagent takes two minutes, four subagents in sequence take eight minutes, while four subagents in parallel take roughly two minutes, plus the synthesis step. The factor of four speedup is real and felt. On a code review that the developer might run twice a day, the saving across a working week is substantial.
挂钟时间上的节省,直白到可以用算术算出来:每个 subagent 跑两分钟,顺序跑四个要八分钟,并行跑四个加上综合那一步大约两分钟。这 4 倍的加速是实在的、感受得到的。评审这件事一天可能跑两次,折算到一个工作周,节省下来的时间是可观的。
But the time saving is not the most interesting benefit. The more interesting benefit is the quality. Each subagent operates in a context that contains only the material relevant to its dimension. The security-auditor's context contains the diff plus the security-auditor's system prompt, focused on security. The performance-reviewer's context contains the diff plus the performance-reviewer's system prompt, focused on performance. Neither subagent has its attention diluted by considerations that are not its own. The result is that each subagent produces a deeper, more focused report than a single generalist reviewer could produce on the same input. The total review is not just faster; it is better, because each part of it was done by a specialist who was not trying to balance attention across four dimensions at once.
但更值得讲的不是时间,而是质量。每个 subagent 工作的上下文里,只有"与它这一维相关"的材料。security-auditor 的上下文里只有 diff 加它自己的 system prompt,聚焦在安全上;performance-reviewer 的上下文里也只有 diff 加它自己的 system prompt,聚焦在性能上。没有任何一个 subagent 的注意力被"不属于自己的考量"稀释。结果就是:每个 subagent 产出的报告,都比"一个通才评审者面对同一份输入"所产出的更深、更聚焦。整个评审不仅更快,还更好——因为它的每一段都出自一位"不用同时兼顾四个维度"的专员之手。
The orchestrator pattern has a discipline that is worth naming. The main session's job, as the orchestrator, is decomposition and synthesis. The subagents' job is the specialty work. The boundary between these two jobs should be respected. The main session should not attempt to do specialty work itself, even when it could; if a security review is needed, the security-auditor subagent should do it, not the main session. The main session should not attempt to mix specialties inside a single subagent, either; a security-and-performance reviewer is a worse subagent than two narrow ones, because the specialization advantage is forfeited. The orchestrator pattern asks the developer to design subagents narrowly, then trust the design, and let parallelism do its work.
编排者模式里有"纪律"二字值得点出。主 session 作为编排者,做的事是分解与综合;subagent 做的事是专长工作。这两件事之间的边界要守住。主 session 不该"哪怕能做也亲自去"做专长工作——需要安全评审,就派 security-auditor,而不是主 session 自己上。主 session 也不该在某个 subagent 内部"混专长"——一个"既安全又性能"的评审 subagent,比两个窄专长的 subagent 更差,因为"专门化"带来的优势被白白扔掉。编排者模式要求开发者把 subagent 设计得窄、然后信任这份设计,让并行去做它该做的事。

There are limits to parallelism worth knowing. Claude Code can run several subagents concurrently in practice; community guidance from heavy users converges on roughly ten as a practical ceiling before queueing becomes noticeable, although Anthropic has not published a hard cap. Beyond that limit, additional dispatches queue and run as earlier ones finish. Within the limit, the parallelism is genuinely simultaneous: the subagents do not take turns; they execute in independent processes. The cost of running multiple subagents is, naturally, multiplied by the number of subagents. A four-subagent review costs roughly four times the tokens of a single-subagent review. This cost is usually well worth paying, because the time and quality benefits dominate, but it is a real cost and worth being aware of.
并行的边界值得知道。实践中,Claude Code 能并发跑若干个 subagent;重度用户的社区经验大致收敛在"十个左右"——超过这个数,排队的延迟就开始能被感知;不过 Anthropic 并没有公开过一个硬上限。超过这个上限,新的派单会进入队列,等前面跑完再出。在上限以内,并行是真正"同时"的:subagent 之间不轮换,跑在彼此独立的进程里。同时跑多个 subagent 的成本,自然也按数量倍增。一次四 subagent 评审的 token,大约是一次单 subagent 评审的四倍。这份成本大多数情况下完全值得付,因为时间与质量上的好处压过它;但它终究是实在的成本,值得心里有数。
There are tasks for which parallelism is the wrong shape, and recognizing them is part of the discipline. Tasks whose components depend on each other do not benefit from parallel execution; the dependencies force sequential work. A task that involves first reading a database schema, then writing a query against it, then optimizing the query, has a strict order that cannot be parallelized usefully. Tasks whose components share a great deal of context also do not benefit; if every subagent would need to read the same fifty files to do its job, the duplication of that reading across many subagents wastes tokens and time. The right pattern in the dependent case is sequential subagent dispatch, where the output of one subagent becomes the brief for the next. The right pattern in the shared-context case is sometimes a single subagent that handles all the work, or sometimes a careful brief that summarizes the shared context once and passes the summary to each subagent so they do not all need to re-derive it.
有些任务天生不适合并行,识别出它们也是纪律的一部分。组件之间有依赖的任务,无法从并行里获益——依赖关系把工作强行串成顺序。一件"先读数据库 schema、再写查询、再优化查询"的任务,就有严格的顺序,无法有意义地并行。组件之间共享大量上下文的任务,也无法从中获益——如果每个 subagent 都要先读同一份 50 个文件,这种"每个 subagent 都重读一遍"对 token 和时间都是浪费。对"有依赖"的情况,正确模式是顺序派单:上一个 subagent 的输出,成为下一个 subagent 的 brief。对"共享上下文"的情况,正确模式有时是派一个 subagent 把活全干了;有时是写一份精心准备的"共享上下文摘要",一次性传给每个 subagent,让它们不必各自重新推导。
A useful framing for deciding when parallelism applies is this question: would I, as a developer, hire four different specialists for four different parts of this task, knowing that the specialists do not need to talk to each other? If the answer is yes, the orchestrator pattern fits. If the answer is no, because the specialists would need to coordinate continuously, the work belongs in a single subagent or in a sequence. This human-team metaphor maps cleanly onto subagent design, and developers who train themselves to ask the metaphor question quickly learn to recognize which workflows benefit most from parallelism.
判断"什么时候适合并行"有一个好用的框架——问自己这样一个问题:"我作为开发者,会为这件事的四个不同部分各雇一位专员,前提是他们彼此之间不需要交流吗?"如果答案是"会",编排者模式正合适;如果答案是"不会"——因为这些专员需要持续协调——那这件事就该交给一个 subagent,或者走顺序模式。这个"人类团队"类比,能干净地映射到 subagent 设计;训练自己会问这个类比问题的开发者,很快就能一眼看出哪些工作流最受益于并行。
A worked end-to-end orchestration looks like this in practice. The developer types her broad request. The main session, recognizing the orchestratable pattern, identifies the dimensions and dispatches the subagents. The dispatches happen in quick succession, and the subagents begin work simultaneously. The main session, while waiting, sometimes does a small amount of preparatory work, like inspecting the diff itself for the synthesis step. The subagents return their reports as they finish; reports may not arrive in dispatch order, since some specialties take longer than others. The main session collects them, holds them until all are present, and then composes the unified output. The whole interaction takes only marginally longer than the slowest of the four subagents. The developer sees a thorough, multi-dimensional review delivered in roughly the time of one careful pass, and the review reads as if four specialists had been retained for the job, because, in a meaningful sense, four specialists were.
一个"端到端"的编排者流程,实操中是这样的:开发者用宽泛的方式提出请求;主 session 识别出"这是一个可编排的形状",找出涉及的维度,派 subagent;派单一份接一份快速发生,subagent 同时开始工作。主 session 在等的当口,有时会做一点准备性工作——比如亲自扫一眼 diff,方便后面综合。各 subagent 完成的顺序可能和派单顺序不一样,因为有的专长耗时长、有的耗时短;它们一边完成一边把报告送回,主 session 收齐之后,会一直等所有报告都到齐,再合成统一输出。整个交互的耗时,只比四个 subagent 中最慢的那一个多一点点。开发者看到的,是一次彻底、多维的评审——送达的耗时,大致相当于"做一次认真评审"的时间;而读起来,就像是真的请了四位专员——在有意义的层面上,确实就是请了四位。

A concrete example will fix this in the reader's mind. Consider a developer who has just opened a pull request that touches roughly four hundred lines of code in three files. The change introduces a new authentication endpoint. Before merging, she wants a full review. She types into Claude Code, in plain language, perform a full review of this PR covering security, performance, style, and test coverage. The main session reads the request. It recognizes the four named dimensions. It looks at the available subagents and finds matches: security-auditor, performance-reviewer, code-style-checker, test-coverage-analyzer. It dispatches all four with a brief that includes the diff and a directive to focus on the subagent's named dimension.
一个具体例子会让这件事在读者脑子里落地。设想:开发者刚开了一个 PR,跨三个文件、改动约四百行,新增一个认证端点。合并前,她想要一次完整评审。她用日常语言在 Claude Code 里敲:"对这个 PR 做一次完整评审,覆盖安全、性能、风格、测试覆盖。"主 session 读这条请求,识别出里面点名的四个维度,去看可用的 subagent,找到匹配项:security-auditor、performance-reviewer、code-style-checker、test-coverage-analyzer。然后它把四个一起派出去,brief 里都带上 diff,并附一条"聚焦你被点名的那个维度"的指令。
The four subagents begin work simultaneously. The security-auditor reads the new authentication code with attention to OWASP categories. The performance-reviewer scans for hot-path issues, queries inside loops, and unbounded allocation. The code-style-checker reads the diff against the project's style conventions. The test-coverage-analyzer cross-references the diff against existing test files to identify which new code paths are unexercised. Each subagent works in a context that contains only the diff and its own focused system prompt. None of them sees the others' work. Each produces a focused report.
四个 subagent 同时开工。security-auditor 用 OWASP 类目去读新的认证代码;performance-reviewer 扫"热路径问题、循环里嵌查询、无界分配";code-style-checker 把 diff 对照项目的风格规约;test-coverage-analyzer 把 diff 和现有测试文件做交叉对照,找出哪些新增代码路径没有被覆盖到。每个 subagent 的上下文里都只有"diff + 它自己那份聚焦的 system prompt",看不到其他 subagent 在做什么,各自产出一份聚焦的报告。
Roughly two minutes later, the four reports return to the main session in whatever order they finish. The security-auditor flags a missing rate limit on the password reset endpoint and a token expiry that defaults to twenty-four hours rather than the project's standard of one. The performance-reviewer flags nothing significant. The code-style-checker notes two minor style deviations. The test-coverage-analyzer points out that the new password reset endpoint has no test coverage at all. The main session reads all four reports, composes a unified review with sections for each dimension, and presents the result to the developer. Total wall-clock time, from her first prompt to the unified review on her screen, is roughly two and a half minutes. Total human attention required, zero, until the review is ready to read.
大约两分钟后,四份报告按各自的完成顺序回到主 session。security-auditor 标出"密码重置端点没有限流"以及"token 过期默认是 24 小时,而不是项目规范里的 1 小时";performance-reviewer 没有发现重大问题;code-style-checker 指出两处轻微的风格偏差;test-coverage-analyzer 指出"新的密码重置端点完全没有测试覆盖"。主 session 读完四份报告,把它们编成一份统一评审——按维度分节,呈现给开发者。从她敲下第一条 prompt,到屏幕上的统一评审出现,挂钟时间总共大约 2.5 分钟。她要付的注意力,是零——直到评审可以读了为止。

Without the Pattern · 没有这个模式会怎样

Now imagine the same review without the orchestrator pattern. The developer would have asked the main session to do the review directly. The main session would have read the diff, then mentally switched into security mode, then into performance mode, then into style mode, then into test-coverage mode, all in a context that accumulated the residue of each phase. The total wall-clock time would have been closer to ten minutes, because the work was sequential rather than parallel. The total quality would have been lower, because each phase was attended to by a generalist rather than a specialist. And the cost in tokens, while lower, would have been a false economy, because the developer's attention is more valuable than the marginal token spend, and the orchestrated review let her get to her next task seven minutes sooner.
现在想象一下:同一份评审,如果不用编排者模式,会怎样。开发者会直接让主 session 做这件事。主 session 会先读 diff,然后在脑子里"切到"安全模式,再切到性能模式,再切到风格模式,再切到测试覆盖模式——所有这一切,都发生在一个不断累积"每一阶段残渣"的上下文里。总挂钟时间会更接近十分钟,因为是顺序而不是并行;总质量会更低,因为每一阶段都只由一个通才在分心兼顾;token 成本确实更低,但那是一种"虚假的节约"——开发者的注意力比那点边际 token 成本更值钱,而且编排式评审让她提前七分钟进入下一件事。

The orchestrator pattern is not the only multi-subagent pattern, although it is the most visually striking one. A second important pattern is the sequential pipeline, in which the output of one subagent becomes the brief for the next. This pattern applies when the work has a real ordering dependency that cannot be parallelized. A common example: the developer wants to refactor a substantial piece of code, but only after having an architectural review of the current structure to confirm the refactor's direction. The architecture-reviewer runs first; its output, a recommendation about which structure is appropriate, becomes part of the brief for the refactor-specialist that runs second. The two cannot run in parallel because the second one needs the first one's conclusions.
编排者模式不是唯一的"多 subagent 模式",虽然它最显眼。第二个重要模式是顺序管线(sequential pipeline)——上一个 subagent 的输出,成为下一个 subagent 的 brief。这种模式适合那种"工作有真实顺序依赖、无法并行"的情形。一个常见例子:开发者想重构一大块代码,但她希望先有"对当前结构的架构评审"来确认重构方向。architecture-reviewer 先跑,它的输出——"推荐走哪种结构"——成为 refactor-specialist 第二个跑的 brief 的组成部分。两者不能并行,因为第二个的输入是第一个的结论。
The mechanics of sequential pipelines are slightly different from those of parallel orchestration. The main session dispatches the first subagent, waits for its result, integrates the result into the brief for the next subagent, dispatches that one, waits for its result, and so on. The total wall-clock time is the sum of each subagent's time, with no parallelism saving. The benefits are still substantial: each step happens in a focused context, each step's output is shaped by the previous step's output rather than by the noise of an accumulated session, and the pipeline can be reviewed step by step, with the option to stop at any intermediate stage if the work is not going where the developer wants. Sequential pipelines, while slower than orchestrations, are the natural shape of work that has real dependencies, and the developer who recognizes when she is in a sequential rather than a parallel situation will save herself the frustration of trying to force orchestration onto work that does not support it.
顺序管线和并行编排的"机械结构"略有不同。主 session 先派第一个 subagent,等它的结果,把结果整合进下一个 subagent 的 brief,再派出那一个,等它的结果,如此往复。总挂钟时间是各 subagent 时间之和,没有"并行带来的节省"。但它带来的好处仍然不小:每一步都跑在一个聚焦的上下文里;每一步的输出由上一步的输出塑造,而不是被一个"不断累积的 session 噪声"塑造;管线可以一步一步地被审视,任何中间阶段,如果工作偏离了开发者的预期,都有机会停下。顺序管线虽然比并行编排慢,但它正是"工作真有依赖"时的天然形状;能分辨"我这是顺序而非并行"的人,会免去"硬把不该并行的东西套上编排模式"的挫败感。
A third pattern, which is a hybrid of the first two, is worth naming briefly. The map-reduce pattern dispatches several subagents in parallel on independent components of a task and then dispatches a final subagent, sequentially, to synthesize their outputs. Sometimes the synthesis is straightforward enough for the main session to do directly, in which case it is just the orchestrator pattern. Sometimes the synthesis is itself a substantial specialty, such as composing a coherent design document from several focused reports, in which case a synthesis subagent is worth defining. The map-reduce pattern shows up most often in larger codebases, where the inputs are too varied for a single specialist to read in full. Different parallel subagents read different sections; a synthesis subagent receives their reports and produces the final output. The pattern is more elaborate, but the underlying principles are the same: independent work in parallel where possible, dependent work in sequence where required, focused contexts at every stage.
第三种模式,介于前两种之间,值得简短给它起个名字:map-reduce 模式。它先并行派几个 subagent,各自处理任务里独立的部分,然后再(顺序地)派一个最后的 subagent 去综合它们的输出。有时综合本身简单到主 session 直接做就行,那就还是编排者模式;有时综合本身就是一门分量不轻的专长——比如把几份聚焦的报告编成一份连贯的设计文档——这时候就值得专门定义一个"synthesis" subagent。map-reduce 模式在大代码库里出现得最多——那里输入过于多样,一个专员读不过来:并行 subagent 各自读自己那一段,synthesis subagent 接住它们的报告,产出最终输出。模式本身更复杂,但底层原则没变:能并行就并行,有依赖就顺序,每一阶段都跑在聚焦的上下文里。

A short reflection on what makes orchestration genuinely powerful. The most striking thing about the orchestrator pattern is not the wall-clock saving, although the saving is real and welcome. The most striking thing is what the developer is freed from. She no longer has to be the one who remembers all the dimensions a thorough review should cover. The pattern itself remembers them. She no longer has to mentally context-switch between security thinking and performance thinking and style thinking, because the subagents handle each dimension in its own thread. Her attention, which was previously distributed across all the dimensions she cared about, can be concentrated on whatever the unified output most demands of her. She becomes, in effect, a senior engineer reading reports written by competent specialists, rather than a junior engineer trying to be all four specialists at once. The transformation in working experience is not just a productivity improvement; it is a change in the kind of cognitive work she is asked to do, and developers who experience it for the first time often describe the shift as the moment Claude Code stopped feeling like a chat interface and started feeling like an environment.
简短聊一下"编排者模式真正强大的地方"。它最显眼的地方,不是挂钟时间的节省——虽然那也是真实且受欢迎的。它最显眼的地方,是开发者被解放出来。她不再需要亲自去记"一次彻底评审该覆盖哪些维度"——模式本身替她记着;她不再需要在脑子里从"安全思维"切到"性能思维"再切到"风格思维"——subagent 各自在自己的线程里处理各自的维度。她原本被摊薄在"所有她关心的维度"上的注意力,可以集中到统一输出最需要她投入的地方。她在效果上变成了"一位资深工程师,读着由胜任的专员写就的报告",而不是"一位初级工程师,试图一个人扮四角"。这种工作体验上的转变,不只是生产力的提升,更是她被要求去做的那类认知工作本身的改变——很多开发者第一次体会到这种转变时会这样描述:"就是这一刻,Claude Code 不再像一个聊天界面,而像一个环境。"

When Not to Orchestrate · 什么时候不该编排

A final note, before this chapter closes, on when not to reach for orchestration. The orchestrator pattern carries overhead. Dispatching four subagents and synthesizing their outputs is more elaborate than asking the main session to do a small task directly. For small tasks, the overhead is not worth paying. A quick code review of a fifty-line patch does not need four subagents; the main session can handle it directly. A trivial documentation update does not need a documentation specialist; the main session is fine. The orchestrator pattern earns its keep on substantial tasks, where the parallelism saving and the specialization benefit are worth the dispatch overhead. The developer who reaches for orchestration appropriately, and refrains from reaching for it on tasks that do not justify it, will have the best experience.
本章收尾前,还要说一点:什么时候不该用编排。编排者模式本身有开销——派四个 subagent、再综合它们的输出,比"让主 session 直接做一件小事"要复杂得多。对小事来说,这笔开销不值得付。五十行 patch 的快速评审,不需要四个 subagent,主 session 直接做就够;琐碎的文档更新,不需要一个文档专员,主 session 自己就行。编排者模式只有在大体量任务上才回本——那里并行的节省和专门化的好处能压过派单开销。能"该用就用、不该用就克制"的人,体验是最好的。
A useful rule of thumb is the five-minute test. If the developer would spend more than five minutes on the task as a single sequential pass through the main session, the orchestrator pattern is probably worth considering. If she would spend less than five minutes, orchestration is probably overkill. The threshold is not exact, and individual judgment varies, but the rule prevents both common mistakes: orchestrating tiny tasks where the dispatch overhead dominates, and serializing large tasks where the parallelism would have produced real savings. With practice, the developer stops needing the rule, because the right shape of work for orchestration becomes visible at a glance. Until that intuition has set in, the five-minute test is a reasonable working approximation.
一条好用的经验法则叫"五分钟测试"。如果开发者自己一个人顺序做这件事要花超过五分钟,那么编排者模式大概值得考虑;如果只要不到五分钟,编排大概率是杀鸡用牛刀。门槛不是死数,个人判断也会有出入,但这条规则可以同时防止两种常见错误——在小任务上"派单开销盖过收益"、在大任务上"本可并行的却被迫串行"。练上一阵之后,这条规则就不必再挂着——编排适合的形状会"一眼可见"。在那种直觉还没稳之前,"五分钟测试"是一个合理的工作近似。

A second observation worth keeping in mind is that orchestration scales with the developer's familiarity. New users of subagents tend to under-orchestrate, treating the main session as the default and reaching for subagents only on the most obvious cases. Experienced users tend to orchestrate naturally, recognizing the orchestratable shape of work in their first or second pass through a problem. The transition from the first state to the second takes only a few weeks of deliberate practice, and the practice is enjoyable rather than tedious, because every successful orchestration produces a noticeable, satisfying acceleration of work that would otherwise have been slow.
第二条值得记在心里的观察是:编排这种"能力"会随着开发者的熟练度而增长。新接触 subagent 的用户倾向于"编排不足"——把主 session 当默认,只在最明显的几种情况里伸手去用 subagent;熟练用户则会自然地编排,在面对一个问题的第一遍、第二遍里就识别出"可编排"的形状。从前者到后者的过渡,只需要几周有意识的练习;而这种练习并不令人疲倦,因为每一次成功的编排都会带来"原本很慢的事被显著加速"那种可感知的满足。
One final reflection on this chapter, before moving to the inventory of specialists. The orchestrator pattern is the visible face of subagents, the part that produces the most striking demonstrations and the most quotable speedups. But the deeper value of subagents, the value that compounds quietly across months of use, is not the speed. It is the consistent quality. A library of well-designed specialists produces consistently high-quality work because each specialist has been designed for its specific role, and the design is preserved across every invocation. The developer who has installed a serious subagent library is not just faster. She is more reliably good at her work, because the failure modes that come from overload, distraction, or context pollution have been engineered out of her environment. The reliability is the prize. The speed is a happy side effect.
在过渡到"专员清单"那一章之前,再留一段反思。编排者模式是 subagent 的"面子"——它造就了最抓眼球的演示、最值得引用的加速。但 subagent 更深层的价值——那种"在几个月里悄悄复利"的价值——不是速度,而是始终如一的质量。一套精心设计的专员库能稳定地产出高质量的工作,因为每位专员都是为它那个特定角色设计的,而这份设计在每一次调用里都被保留下来。装下了一套"像样的 subagent 库"的开发者,不只是更快——她更稳定地做得好;因为"过载、分心、上下文污染"带来的失败模式,已经从她的环境里被工程化地排除了。可靠性才是奖赏;速度只是顺带的好处。

Composition in Action · 组合在行动

The result is strikingly better than what either component could produce alone. A skill alone, fired in the main session, would shape the output toward project conventions, but the output would be subject to context pollution from whatever else the main session was working on. A subagent alone, dispatched on the same task, would produce well-isolated, generally good tests, but it would not know the project's specific conventions and would have to guess. The combination has both: convention-correct tests, produced in a clean context, by a specialist who treats the work seriously. This is the composition pattern in its simplest form, and once a developer sees it work even once, she will not want to design subagents that do not know how to use skills.
这种结果,比"任何一方单独能产出的"都明显要好。Skill 单独、在主 session 里触发,确实会让输出向项目规约靠拢,但那份输出仍会被主 session 里其他事情的"上下文污染"影响。Subagent 单独、被派去做同一件事,确实能产出"隔离良好、整体不错"的测试,但它并不知道这个项目的具体规约,只能猜。两者的组合同时拥有这两点:规约准确的测试、由"把工作当回事"的专员、在干净的上下文里产出。这就是组合模式最简单的形态;一旦开发者哪怕只看它工作一次,她就再也不想设计"不懂用 skill"的 subagent 了。
There is a design principle that follows from this and that should guide every subagent the developer writes from now on. Subagents should be designed as roles, not as repositories of project knowledge. A test-writer subagent should know how to be a senior test engineer in general; it should not know that the project uses Vitest rather than Jest, or that mocks should be placed in a specific directory, or that the team prefers a specific assertion library. Those are project facts, and they belong in skills. The subagent provides the role; the skill provides the project-specific knowledge. When the role meets the project, the composition produces the right behavior.
由此引出一条设计原则,它应该从今往后指导开发者写的每一个 subagent:subagent 应该被设计成角色,而不是"项目知识的容器"。一个 test-writer subagent 应当知道"如何作为一位高级测试工程师",而不应当知道:这个项目用的是 Vitest 而不是 Jest、mock 要放在某个特定目录、团队偏好某个特定的断言库。这些是项目事实,属于 skill。subagent 提供角色,skill 提供项目特定的知识。当角色与项目相遇,组合就产出正确的行为。
This principle has a second-order effect that is worth naming. A subagent that contains project-specific knowledge becomes specific to that project, and its usefulness drops as soon as the developer moves to a different project. A subagent that contains only the role, with project-specific knowledge factored into skills, is portable. The same test-writer subagent works in five different projects, because the role is the same in each, and the project-specific conventions are loaded as skills from each project's own .claude/skills directory. A small library of well-designed, role-only subagents at the user level, combined with project-specific skills in each project, gives the developer the best of both worlds: stable, portable specialists, and project-appropriate behavior in every project she works in.
这条原则有一个值得点名的"二阶效应"。一个把项目特定知识塞在自己体内的 subagent,会变得"只适用于那个项目";开发者一切换到另一个项目,它的价值就立刻下降。一个只装"角色"、把项目特定知识抽到 skill 里的 subagent,才是可移植的。同一份 test-writer subagent,可以在五个不同的项目里都工作得好——因为"角色"在每个项目里都一样,项目特定的规约由"每个项目自己的 .claude/skills 目录"以 skill 形态加载进来。一套小而精、只装"角色"的 subagent 库放在用户级,再加上每个项目里"项目级"skill——开发者就同时拿到了两样最好的东西:稳定、可移植的专员,以及"在每个项目里都符合项目实际"的行为。

The Architectural Principle · 架构原则

There is a deeper architectural principle visible here, which is worth naming explicitly because it will guide every later chapter of the book. The composition pattern is an instance of the broader principle of separation of concerns. Skills hold project knowledge. Subagents hold roles and isolate contexts. Neither system tries to do the other's job. When a workflow needs both kinds of capability, the systems compose, and the composition produces capabilities that neither alone could provide. This is the same principle that underlies every well-architected piece of software, applied to the design of a Claude Code environment. Developers familiar with separation of concerns in their own code will recognize the principle immediately and find the composition pattern intuitive. Developers unfamiliar with it will, by working through this part of the book, internalize the principle by seeing it applied to a domain where its benefits are immediate and visible.

A second design discipline that emerges from the composition pattern concerns versioning. Skills and subagents that are designed to compose with each other should evolve together. If the developer changes the conventions encoded in a skill, the subagents that depend on that skill may need to be checked to ensure their behavior still aligns. Second-Order Benefits · 二阶收益

There is a second-order benefit to the composition pattern that becomes visible only after a developer has lived with a composed library for a few months. The benefit is that the library becomes self-documenting in a way that monolithic configurations are not. A new developer joining the project can read the .claude/skills directory to learn the project's conventions; reading the SKILL.md files is essentially reading a structured guide to how the team prefers to work. Together, the two directories form a piece of working documentation that is more accurate than any wiki, because the documentation is the configuration the tool actually uses. This self-documenting property is a substantial benefit for any team that grows, because it lowers the cost of onboarding new members and reduces the gap between what the team says it does and what the team actually does.
